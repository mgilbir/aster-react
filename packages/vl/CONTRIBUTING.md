# Working on `@aster-charts/vl`

This page is for people who change the compiler. It is not part of the published package: the npm page is [README.md](README.md),
which states the contract (what compiles, what throws). The repository-wide workflow is [CONTRIBUTING.md](../../CONTRIBUTING.md); how
to debug a failing conformance case end to end is in [docs/RUNBOOK.md](../../docs/RUNBOOK.md).

## Where the contract is implemented

| Contract in the README | Source (`packages/vl/src`) |
|---|---|
| `compile` never mutates its input | `compile.ts` clones the spec once, up front; every later edit lands on the private copy |
| Unsupported or invalid input throws a `VLCompileError` naming the feature and its path | `validate.ts`: allow-lists derived from one table each, shared message templates; it runs before anything is compiled. Then `schema.ts`: every value is held to vega-lite's JSON schema through `schema-table.ts`, which `scripts/schema-table.mjs` generates from the pinned vega-lite (run `node packages/vl/scripts/schema-table.mjs` after upgrading it; `test/schema-table.test.ts` fails until you do). The forms vega-lite reads beyond its schema, which Aster draws as vega-lite does, are that script's `EXTENSIONS`: each names the differential that pins it, and an example the plain schema refuses |
| `{"expr"}` is an expression only where the schema takes an ExprRef | `schema.ts` records the values given where the schema takes any value (`isLiteralValue`); `compile.ts` `exprRefsToSignals` leaves them literal |
| Composition nesting | `NESTING` in `validate.ts` (parent kind to the child kinds it takes: the schema's, and what vega-lite compiles beyond it; the compiler implements all of them, and the nestings it still refuses are individual checks listed under "Throws") |
| Field names never reach an expression or a generated name unescaped | `names.ts`: every place that lets a user-supplied field name into an expression string, a generated field name or a signal name goes through it |
| Marks and channels | `compile.ts` (the unit compiler), `channels.ts` (which marks draw which channels), `orient.ts`, `scaletype.ts`, `scaleprops.ts`, `scaleconfig.ts`, `titles.ts` |
| Composite marks (boxplot, errorbar, errorband), overlays | `composite-marks.ts`, `composite.ts` |
| Composition (concat, repeat, facet) | `embed.ts` renames every child-local scale, signal and dataset so siblings cannot collide, including names inside expression strings |
| Transforms, predicates, time units | `transforms.ts`, `predicate.ts`, `timeunit.ts` |
| Selections | `selection.ts` (the parameter resolved against its unit), `selection-model.ts`, `selection-signals.ts`, `selection-marks.ts`; event selector strings: `event-selector.ts` |
| Maps | `geo.ts`, a port of vega-lite's `compile/projection` with the `geojson` / `geopoint` data nodes and the `geoshape` post-encoding transform |
| Animation | `animation.ts`: the `time` channel, the timer selection and the `{filter: {param}}` transform |
| Dataflow optimizations vega-lite runs over the whole spec | `optimize.ts` |

## The consumption check (what is accepted is read, or refused)

`validate.ts` says which properties may appear in a spec. `consume.ts` holds the compiler to reading every one that does: the compile's copy
of the spec is armed while it is made (`cloneSpecStructure` with `ARMING`; validation reads it under `peek`), so that each property of it is
an accessor whose first read records it as consumed, and at the end of the compile `refuseUnconsumed` throws a `VLCompileError` for every
property nothing read (`<path>: is valid Vega-Lite but @aster-charts/vl does not implement it here, so it would be ignored`). So a feature the
validator lets through and the compiler never looks at is refused instead of being compiled silently wrong, and the refusals are generated by
the code that compiles: a new property needs no entry in a list beside it.

The check runs in every compile, so it is kept cheap, and its cost is measured with the compile's (`perf(vl)` commits name the numbers):
no second copy of the spec, one hidden record of arrays per object (no object per property), one accessor per key name shared by every
object (objects of one shape keep one hidden class), and paths worked out only when there is something to refuse. Settling a property into
plain data on its first read was measured slower than leaving the accessor in place (V8 reshapes the object on every settle).

What counts:

- A property whose value is a scalar, an array of scalars or an empty object must be read. A property that holds objects (a channel
  definition, an axis, a layer, a transform list) is consumed through what is below it: moving such values around needs no bookkeeping.
- `config` is not checked (a config block applies where the spec has something it configures; validate.ts checks its keys), nor are the
  rows (`data.values`, `datasets` entries), which compile never reads.

Writing compile code under the check:

- A read is a consumption, whatever form it takes (`spec.width`, a destructuring, `Object.entries`, a spread, `JSON.stringify`). Read a
  property where its value is used.
- Code that only looks (a decision about the spec's shape, a comparison, a cache key, a walk that collects names) runs inside `peek(() => ...)`.
- Code that rewrites a spec object to be compiled further copies it with `derive(src, over)`, `deriveWithout(src, keys)`, `pick(src, keys)`,
  `transfer(src, key, dst)` or `deriveDeep(v)` instead of a spread, a destructuring or `structuredClone`: the copy's properties stand for the
  original's until the copy's are read. `merge(base, top)` is `{...base, ...top}` where `top` overrides `base` as vega-lite's merges do
  (the overridden properties are consumed). The normalizing passes (composite.ts, the nested facet and image rewrites) run under `peek` and
  use these; `consuming(() => ...)` reads for real inside a `peek` (a composite mark's own properties are its meaning).
- Where vega-lite itself ignores a property, say so: `ignore(obj, key, why)` consumes it, and everything below it. Each `ignore` names the
  reason and has a case against vega-lite that pins it (a composition operator's `width` / `height`, a channel the mark does not draw, a
  sort under an explicit domain, a layer's data that every layer replaces, a geographic constant, ...). `consumeAll(node)` is for a subtree
  forwarded to Vega as it is.
- To find what consumed a property while debugging, `globalThis.__consumeTrace = (path, stack) => ...` is called for each consumption.

The README's "Throws" list states the refusals that are deliberate; the consumption check covers everything else, generically. Its own tests
are in `test/consume.test.ts`.

## Where it is tested

- Unit tests in `packages/vl/test/`: `validate.test.ts` (refusals), `names.test.ts` (hostile field names), `immutability.test.ts`
  (compiles a deep-frozen copy of every corpus spec, from `corpus/` and `corpus-vega-only/`, so a mutation throws), `structure.test.ts`,
  `selection-composites.test.ts`, `geo.test.ts`, `animation.test.ts` and the rest.
- `readme-refusals.test.ts` reads the "Throws (not supported)" list of [README.md](README.md) (the text between `## Throws (not supported)` and
  `## Known runtime gaps`). Every feature it names must be refused by `compile` with a `VLCompileError`, and the features that used to be on
  the list must not be. To change the list, change the README and the table in the test together; keep both headings.
- Parity against the real vega-lite lives in the conformance package, not here: `packages/conformance/test/vl-mark-channels.test.ts` compiles
  every mark x channel x definition (`vl-mark-channels-space.ts`) with vega-lite 6.4.3 and with `@aster-charts/vl` and compares the compiled
  scales, axes and legends, the rows and the SVG; `vl-predicate.tz.test.ts` compares the rows and expressions of every predicate form, including
  every UTC time unit read in local time, under the zones of `pnpm test:tz`; the `vlx-geo-*` specs of `packages/conformance/corpus` hold a case
  per map feature. `pnpm conformance-vl` renders the whole Vega-Lite corpus through vega-lite and through `@aster-charts/vl` and compares both.
- `packages/conformance/corpus-vega-only` is where a Vega-Lite spec would live while the Aster runtime cannot yet render vega-lite's own Vega for it
  (it is held to the real-vega check only). It is empty today; its README says how to record a case.
